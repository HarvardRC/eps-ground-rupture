# ADR-0003: Production query engine — AWS Athena over S3 Parquet

- **Status**: Accepted
- **Date**: 2026-05-24
- **Deciders**: Michael Bouzinier (project owner)

## Context

Production dashboards need to query tidy datasets via SQL. We want
serverless operation, native connectors in both Tableau Cloud and Superset,
and minimal infrastructure to maintain. Data sizes are small (low tens of
MB compressed Parquet).

## Decision

Store Parquet under an S3 prefix and query it with **AWS Athena**
(serverless Trino) via the AWS Glue Data Catalog. Table definitions are
generated by the pipeline and applied to Glue (see ADR-0007).

## Alternatives considered

- **Redshift Spectrum** — same idea but requires a Redshift cluster running
  24/7. Excess infrastructure.
- **Trino self-hosted** — open-source Athena equivalent. Adds an ops layer
  we don't need at this scale.
- **DuckDB-only in production** — single-machine; doesn't fit
  multi-consumer dashboards.
- **Snowflake / BigQuery** — strong engines but introduce per-query cost,
  vendor lock-in, and storage migration.
- **PostgreSQL warehouse** — row-store engine class, would diverge from
  dev (see ADR-0011).

## Consequences

- No cluster to operate. Athena bills per-TB-scanned (negligible at our
  size).
- Glue catalog becomes the registry; DDL must be applied there
  (manually for now — see "Known gaps" in `docs/setup.md`).
- SQL dialect is Trino — generally portable to other Trino-family engines
  (Starburst, self-hosted Trino, Presto).
- AWS coupling. Moving cloud would require re-platforming the query layer
  but not the Parquet data.
