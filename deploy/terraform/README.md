# Terraform — AWS data layer

Provisions, per environment (`dev` / `prod`):

| Resource | dev | prod |
|---|---|---|
| S3 bucket | `eps-ground-rapture-dev` (destroyable, unversioned) | `eps-ground-rapture-prod` (protected, versioned) |
| Glue database | `eps_ground_rapture_dev` | `eps_ground_rapture_prod` |
| Glue tables | one per Parquet dir — currently 5; see `tables.json` | same |
| Athena workgroup | `eps-ground-rapture-dev` | `eps-ground-rapture-prod` |

The bucket holds the Parquet under `processed/<table>/` and Athena query
results under `athena-results/` (auto-expired after 30 days). The bucket
is encrypted (SSE-S3) with all public access blocked.

Uses the AWS profile **`urc`**; region comes from the profile
(`~/.aws/config`, currently `us-east-1`).

## Layout

```
deploy/terraform/
  tables.json        ← generated by the pipeline; committed (schema lockfile)
  modules/data/      ← the reusable module (bucket + Glue + Athena)
  envs/dev/          ← thin root, local state
  envs/prod/         ← thin root, local state
```

## Schema single-source-of-truth (read before editing)

`tables.json` is **generated** by `poetry run egr-build` (from the actual
Parquet schemas, via `eps_ground_rupture.register`). Do not hand-edit.
After a pipeline change that alters a table's columns:

```bash
cd subprojects/python && poetry run egr-build     # regenerates tables.json
cd ../../deploy/terraform/envs/dev && terraform apply
# re-upload the data (see below) — column ORDER must match the files
```

Column names in Athena are **sanitized** versions of the Parquet field
names (`Us - Ud` → `us_ud`, `SS_uc+` → `ss_uc_plus`, …) because Athena
forbids spaces/special characters. The SerDe maps columns **by ordinal
position** (`parquet.column.index.access = true`), so the Parquet files
keep their original names — DuckDB / Spark / Tableau local paths are
unaffected. Consequence: never reorder columns in the pipeline without
re-running both `egr-build` and `terraform apply` and re-syncing the data.
Each Glue column's *comment* records the original Parquet field name.

Note: three columns are Athena **DDL** reserved words — `set` (dem),
`date` and `references` (sure). Plain `SELECT`s work even unquoted
(double quotes are always safe in DML), but all three must be
backtick-quoted in hand-written DDL such as CTAS / `ALTER TABLE`.

## Deploy

Via Gradle (this directory is the `:deploy:terraform` subproject):

```bash
./gradlew :deploy:terraform:planDev       # read-only preview
./gradlew :deploy:terraform:applyDev      # auto-approved (dev only)
./gradlew :deploy:terraform:syncDataDev   # aws s3 sync data/processed/ → bucket
./gradlew :deploy:terraform:outputDev     # bucket / database / workgroup names

./gradlew :deploy:terraform:planProd
./gradlew :deploy:terraform:applyProd     # interactive yes/no — run from a terminal
./gradlew :deploy:terraform:syncDataProd
```

(`init<Env>` runs automatically when `.terraform/` is missing. Override
binary locations with `TERRAFORM_BIN` / `AWS_BIN` env vars or
`-Pterraform.bin=` / `-Paws.bin=`; override the profile with
`-Paws.profile=`.)

Or with raw Terraform:

```bash
cd deploy/terraform/envs/dev      # or envs/prod
terraform init                    # first time only
terraform plan
terraform apply
```

(If you instead want the *manual* `dashboards/sql/athena.sql` route — e.g.
no Terraform on the machine — regenerate it with values matching this
layout first: `poetry run egr-build --database eps_ground_rapture_dev
--s3-prefix s3://eps-ground-rapture-dev/processed/`. The defaults
intentionally contain `CHANGE_ME` so a mismatched copy-paste fails loudly
rather than silently querying an empty location.)

Then upload the data (from the repo root; command also printed as the
`sync_command` output):

```bash
aws --profile urc s3 sync data/processed/ s3://eps-ground-rapture-dev/processed/ --exclude '*.gitkeep'
```

Smoke-test in Athena (console or CLI; select workgroup
`eps-ground-rapture-dev`):

```sql
SELECT COUNT(*) FROM eps_ground_rapture_dev.dem;          -- expect ~346,834
SELECT eq_name, COUNT(*) FROM eps_ground_rapture_dev.sure GROUP BY eq_name;
```

## Connecting BI tools

(The bucket's *public access block* does not affect any of this: it only
forbids anonymous access. BI tools authenticate with IAM credentials and
talk to the Athena API; Athena reads the Parquet server-side under those
permissions, and the driver fetches result files from `athena-results/`
the same way. Required permissions: `athena:StartQueryExecution/Get*`,
`glue:GetDatabase/GetTable(s)`, `s3:GetObject`+`ListBucket` on the bucket
and `s3:PutObject` on `athena-results/*`.)

- **Tableau**: Connect → Amazon Athena. Server
  `athena.us-east-1.amazonaws.com`, port 443, S3 staging directory
  `s3://eps-ground-rapture-<env>/athena-results/`, workgroup
  `eps-ground-rapture-<env>`, catalog `AwsDataCatalog`, database
  `eps_ground_rapture_<env>`. Credentials: access key for the `urc`
  identity (Tableau's Athena connector doesn't read `~/.aws` profiles
  for credentials).
  Gotcha: the connector doesn't pass the region to the JDBC 3.x driver
  either — without a fallback you get *"Unable to load region from any
  of the providers in the chain"*. Fix: a region-only default section in
  `~/.aws/config`:

  ```ini
  [default]
  region = us-east-1
  ```
- **Superset**:
  `awsathena+rest://athena.us-east-1.amazonaws.com:443/eps_ground_rapture_<env>?s3_staging_dir=s3://eps-ground-rapture-<env>/athena-results/&work_group=eps-ground-rapture-<env>`
- **DbVisualizer / any JDBC client**: install the Amazon Athena JDBC
  **3.x** "with-dependencies" jar (driver class
  `com.amazon.athena.jdbc.AthenaDriver`), then connect with userid/password
  blank — the 3.x driver reads `~/.aws` profiles natively:

  ```
  jdbc:athena://Region=us-east-1;Catalog=AwsDataCatalog;Database=eps_ground_rapture_<env>;WorkGroup=eps-ground-rapture-<env>;OutputLocation=s3://eps-ground-rapture-<env>/athena-results/;CredentialsProvider=ProfileCredentials;ProfileName=urc
  ```

## State

Local per-env state (`envs/*/terraform.tfstate`, gitignored). Fine for a
single operator; if this ever becomes a team setup, move to an S3 backend
(separate state bucket + DynamoDB lock) — deliberately out of scope now.

## Costs

Athena bills per TB scanned (the whole dataset is ~11 MB Parquet —
negligible); S3 pennies; Glue catalog free at this scale. No always-on
infrastructure.
